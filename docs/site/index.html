A research project, explained simply

Find the bug in a quantum circuit. Fix it. Prove it.

A quantum program is a short list of steps called gates. One wrong gate and the answer is wrong. This project builds a tool that finds the wrong step, repairs it with the smallest change, and then checks the fix very carefully.

The idea

Think of a recipe with one wrong step

A quantum circuit is like a recipe. Each gate is one step. If one step is wrong, the dish is wrong. A repair tool should find that step and change it, and change nothing else.

The hard part is honesty. A tool that is allowed to read the answer key can just copy it. So in this project the repair tool never sees the correct circuit. It can only ask one kind of question: "how close is my circuit to the right behaviour?" Every question is counted.

Problem

Bugs hide

Quantum results are fuzzy numbers, so a wrong gate is hard to spot by reading the code.

Idea

Ask, don't peek

The tool only gets a score from a hidden test. It tries small edits and keeps the ones that raise the score.

Proof

A strict judge

A separate judge checks the final circuit exactly, on the real hardware rules, and with noise.

Honesty

Limits are listed

The test circuits are small and simple. We say so, and we show where the tool still fails.

How the tool works

The wall that keeps it fair

The correct circuit is behind a wall. Only the judge can see it. The repair helper gets a small window: a score for each circuit it tries, plus a counter that tracks how many scores it asked for. We never tell it the type of bug.

Why not just trust the score?

The repair helper only sees a few test inputs, so it could fool itself. The judge checks the whole circuit and also uses hidden inputs. We measure the gap between the two to see how often this happens.

A clever trick

Find the best angle in just three questions

Many gates turn a qubit by an angle. If the angle is wrong, how do we find the right one? Trying many angles is slow. But there is a shortcut: the score always follows a smooth wave as the angle changes. A wave is fully known from three points. So we ask three questions, fit the wave, and jump straight to its top.

The three questions are asked at 0, 120 and 240 degrees. The formula behind the wave is score = c0 + c1 cos(angle) + s1 sin(angle). Three numbers, three points, one exact answer.

Going further

Beyond simple circuits

Real quantum programs do more than apply gates. They measure qubits, react to the result with an if-statement, reset qubits to reuse them, and loop. The first test set could not even describe these. So we built a second one with 600 such programs, six kinds of bugs, and an exact way to compare what two programs print.

Faults a gate-only check cannot see

If two measurements write to each other's result bit, the gates are exactly the same as before. A check that only compares gates says "fine". In the new test set, 52.7% of the bugs are like this (by definition: a gate-only check ignores measurements, resets and if-statements). The tool fixes 98.4% of them.

How the engine knows what a program prints

It follows every possible measurement result, one branch at a time, and adds up the chances. No random sampling, so the answer is exact. We compared it with the Qiskit Aer simulator on three programs and the difference was only shot noise.

Would a repaired circuit run well on the chip?

The judge only checks that two-qubit gates join neighbours. A better test is to compile the circuit to the chip's own gates and use the chip's published error rates to estimate the chance that the whole circuit works (ESP). Pick a circuit family.

Be careful with these numbers

What this project does not prove

Each limit below was first listed as a gap. Here is what was done about it and what is still open.

Bugs are small

Wider now, still injected

The second test set adds wrong measurement wiring, wrong if-conditions, missing resets, loop errors and programs with two or three bugs at once. But every bug is still put in by a script, and the fix lies in the tool's search space. 92% there, 98.8% on the first set: neither shows general repair skill. Several bugs at once (67%) is where it breaks.

Only part of the language

More covered, not all

The judge now also handles measurement, reset, one-bit if-statements and fixed loops exactly. Still missing: while loops, conditions on several bits, timing, and a noise check for such programs.

Small models, few real bugs

Tried, still thin

On the same 60 test circuits, writing the repaired circuit themselves, a 1.5-billion-parameter local model fixed 16.7% and two small Gemini models 43% and 52% (the tool's guided search: 98.3%). When those Gemini models instead called the tool's checking steps they reached 90-95%, but the same steps with no model at all reach 98.3%, so the tools, not the model, do the work. These are small models on a free plan, not a ruling on larger ones. On five real bugs from the Bugs4Q collection the tool fixed three; the two it missed are a QFT with a missing swap and four missing H gates. HornBro has public code. A first run on Colab failed on a missing package of its own, so there is no comparison yet; a rerun is needed. UnitAR and QBugLM have no public code. We make no claim to beat any of them.

A model of a chip

Better estimate, still no chip

A saved calibration snapshot now gives a success estimate. It shows the simple qubit layout is much worse than a good one (QFT: 0.34 against 0.76), so "valid on the chip" in the judge is looser than "runs well". No circuit was run on a real quantum computer.

Questions

Plain answers

What is a qubit, gate or circuit?

A qubit is the quantum version of a bit. A gate is one operation on one or two qubits. A circuit is a list of gates. The program here is written in OpenQASM 3, a plain text format for circuits.

What was wrong with the first results (77.5% and 99.1%)?

The repair step was allowed to read the correct circuit and return it. Baseline results were typed in by hand, attempt counts were unequal, and bug labels leaked. After fixing all that we found the test set itself was broken. Those old numbers are kept in legacy_v1/ for the record only.

What does "fixed" mean?

The judge accepts a circuit only if it parses, has the right number of qubits, follows the chip's connection and timing rules, has no gate pair that cancels itself, matches the correct circuit exactly (up to a global phase), and behaves the same under noise.

Why count the questions?

Searching costs something. If a tool asks a million questions it is not really repairing, it is guessing. Reporting the count keeps the comparison fair.

What is a physical (hardware) fault?

Two kinds: a circuit that uses a connection the chip does not have (it must be re-routed with swaps), or a wait step so long that the qubits forget their state.

Can I trust a repair made from tests only?

Less than one made from a reference circuit. Passing tests does not prove the circuit is right. The tool says this in its report. Use tests that include phase-sensitive inputs.

How do I run it?

pip install -r requirements.txt, then python -m src.cli repair examples/ghz3_buggy.qasm --tests examples/ghz3_tests.json. Run pytest -q for the 82 tests.

What is a program with measurements and if-statements?

Some quantum programs measure a qubit in the middle, then act on the result, for example "if the bit is 1, flip another qubit". Teleportation works this way. Such programs cannot be compared as plain matrices, so the second test set compares what they print, exactly.

What does the chip estimate (ESP) mean?

ESP is the estimated chance that every gate and every readout in the compiled circuit works, from the chip's published error rates. It is a quick estimate from one saved snapshot of a simulated device, not a test on real hardware.

Why was no real quantum computer used?

That needs an IBM Quantum account, a saved set of calibration data, and waiting time in a queue. None of those are in this repository, so the chip results are estimates.

Why is there no comparison with HornBro, UnitAR and QBugLM?

HornBro's code is public, but it needs Linux and its own Python setup, so it is run in a separate Colab notebook; the first run failed on a missing package (not a HornBro result), so no number is shown until it is rerun. UnitAR and QBugLM have no public code that we could find. Rebuilding them from the papers would not be a fair test of the real tools.
